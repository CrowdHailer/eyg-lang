01 / The proposition

Know what your
agents can do.

Put the permission check where an operation becomes an effect. Keep the facts that explain the decision.

Typed

Policy and program agree on the shape of requests and results.

Explicit

The runtime decides which effects exist and how they execute.

Explainable

Queries can return the grants that justify a permitted action.

An implementation-backed proposal. Examples and tests are included in this repository.

Audience: teams building agent runtimes. EYG does not reveal an agent's private reasoning. The claim is about the operations it requests and the authority the host chooses to exercise. Authorization evidence and durable audit storage still need a host.

03 / Policy as ordinary code

Join the facts that
justify permission.

rule Permit({tenant, actor, action, resource, role}) {
  var role
  Member({tenant, actor, role}),
  RolePermission({tenant, role, action, resource})
}

The request supplies lexical constants. The query joins trusted membership and permission facts within one tenant.

Empty result → deny. Unknown or caller-supplied “facts” are not authority.

Excerpt from the executable authorization tutorial; the surrounding host authenticates the principal.

The compiler checks schemas and purity. Neither a correct type nor a Table value authenticates a fact. Never merge arbitrary untrusted rules into the policy database: an attacker could simply assert Permit. Rule creation in the examples admits data through a trusted read/write delegation template.

04 / Explain the authority

“Allowed” can come
with a reason.

Team policy ops-read
→ Alice delegates alice-report
→ Agent a1 reads an Atlas report
{actor: "a1", task: "report", action: "read",
 expires: 150, grants: ["alice-report", "ops-read"]}

Selected fields from a tested permission. Store the complete request, trusted snapshot revision, time, policy version, proof, and effect outcome.

The newest delegation is first in the grants list. The proof tracks policy and delegation IDs, not every solver step. Membership, approvals, ownership and task state must remain retrievable through the recorded snapshot. Proofs are ordinary values, not signatures or portable credentials.

05 / Long-running work

A task keeps running.
Its authority can change.

Next requestCurrent factsDecision
Read report at time 100Task running; delegation currentPermit
Same read at time 150Task expiredDeny
Same read after cancellationTask no longer runningDeny
Write instead of readRead-only delegationDeny

Reauthorize every effect from a fresh snapshot. Yesterday's permission is evidence, not a reusable credential.

These are deterministic examples with logical timestamps. Production hosts supply real time and synchronize decisions with execution using transactions or snapshot-version checks when atomic revocation is required. A startup-only check would not provide these guarantees.

07 / Why this helps an executor

One language for
the action and its guard.

Typed composition

Combine ordinary functions and query values. Catch inconsistent relation fields before execution.

Controlled effects

The host can deny, rewrite, or simulate a request through an explicit handler.

Repeatable evidence

Pin code dependencies, retain input snapshots, and replay pure policy decisions.

The advantage is less glue between policy evaluation and program execution.

Content identifiers identify code bytes; they do not prove who authorized a policy. Unpinned named packages resolve to a latest version, so reproducible deployments must use pinned references. Replaying a policy decision does not replay or undo external effects.

EYG and Biscuit protect
different boundaries.

Biscuit primary references: token specification · Datalog and block scoping. Reviewed 2026-10-07.

Biscuit is not merely a string-based permission check: its signed block structure and scoped facts make untrusted offline attenuation possible. EYG's ordinary Table values provide no equivalent cryptographic or origin-scoping guarantee. Do not claim the EYG admission example replaces that mechanism.

09 / Where EYG is the better fit

When you own the executor,
enforce inside the executor.

Choose EYG for a runtime that evaluates agent programs, mediates their effects, and computes application-specific explanations in the same typed language.

Biscuit alone does not supply that program runtime. Its authorizer can decide whether a request is permitted; the application still connects that decision to execution.

Choose Biscuit when you need a portable, verifiable delegation across services. An EYG host could verify a Biscuit token and turn selected claims into trusted policy facts.

The integration described here is an architectural option, not an implemented adapter. Biscuit's microservices delegation model.

This is the scoped answer to “why is this better than Biscuit?” It is better suited to supervising execution when the team controls the interpreter and wants one policy/program model. It is not universally stronger authorization. Combining them could preserve Biscuit's cross-service credential properties while using EYG to enforce local effects.

10 / What the host must still supply

Make the boundary real.

  • Authenticate identities and control which services assert facts.
  • Recheck current authority before effects; record the outcome.
  • Confine physical filesystem access; lexical paths cannot stop symlink escapes.
  • Limit computation, input sizes, and network capabilities.

A pure, well-typed query can still be expensive or non-terminating. A denial is not a full audit log.

Biscuit likewise leaves revocation state management to applications: goals and non-goals.

The example path policy is explicitly lexical; Loam's test filesystem contains no symlinks. The engine currently uses whole-relation rounds, not an optimized indexed solver. This slide distinguishes implementation-backed guarantees from responsibilities of a deployment.

12 / The decision

Review the authority.
Gate the effect.
Keep the evidence.

EYG puts these pieces in reach of the team building the agent runtime. Its strongest case is the connection between policy and execution.

Start with the executable tutorial →

Close by asking which runtime boundary the audience owns. If they only issue credentials to independent services, Biscuit may be the better first component. If they execute generated programs themselves, EYG's effects and typed policies provide a direct place to exercise oversight.
