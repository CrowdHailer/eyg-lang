EYG cloud Shell Configuration Artifacts Docs

Agents and automations you can read.

EYG cloud puts agents in your team chat, Slack, Discord or WhatsApp, and runs triggers on what happens in GitHub, Sentry, your server logs, Bluesky, feeds and any service that can call a webhook. Everything it may do is written in EYG, a small language for programs whose every side effect can be checked, and checked by policies you own, so the people stay in charge.

Agents that choose to speak

Each channel’s checked handler decides which events reach its agent. It only posts when it has something to say, by running a program that performs Post.

Triggers on everything

A trigger is a pure EYG function from an event to true or false, and a script to run. Events come from chats, GitHub, Sentry, webhooks such as log drains, Bluesky, RSS, Hacker News and Lobsters.

Policies, not permissions screens

Each channel has a shell: a record of gates, one per effect. Gates are functions you can read and test. Every gate is required and type checked; start with cloud.reject_all and override the effects to allow.

Answers without access

Dataclips are named functions with their own policy. A channel with no database access calls one to answer a question, and its author decides which rows ever leave the database.

One API for people and agents

The cloud is configured with effects. You use them in the web shell, your scripts use them over HTTP and a trusted channel's agent uses them for you.

Words used here

EYG
The language everything here is written in. Programs reach the world only through effects, so what a program may do can be decided before it runs.
Effect
One thing a program asks the cloud to do, such as Post, Fetch, WriteFile or SQLite.
Gate
A function that receives an effect's value and passes it on, changes it, answers it without performing it, or rejects it.
Workspace
One team's agents, files, secrets and connections, configured by its workspace.eyg.
Channel
A chat channel, each has its own agent conversation, triggers and shell.
Connection
A chat the workspace is in, the example chat, Slack, Discord or WhatsApp, or a service whose events reach a channel's triggers: GitHub, Sentry, webhooks, Bluesky, feeds, Hacker News, Lobsters.
Shell
A policy, the record of gates a program runs with, one per effect it may use. Each channel has one, and so does each person.
Web shell
The page where you type and run EYG with your shell, at /shell.
Trigger
A pattern, a pure function from an event to true or false, and a script, a function run when the pattern is true.
Binding
Running the web shell as one channel, with that channel's shell instead of yours, to do what its agent could. Your own shell decides which channels you may bind to.
Dataclip
A named function in workspace.eyg with its own shell, that channels call to read data they cannot reach directly.
cloud.eyg
The cloud's configuration: its workspaces and the shells people can be given.
workspace.eyg
One workspace's configuration: model, connections, channels, their shells and triggers, and dataclips.

Quick triggers

Fill in a card and open it in the web shell. The shell binds to the channel, so the trigger is installed with that channel's policy. Press Ctrl+Enter, or Cmd+Enter on a Mac, to install it, the shell then lists the channel's triggers. A card adds a trigger while the cloud runs, with AddTrigger. To keep it after a restart, and review it like code, copy it into the channel's triggers in workspace.eyg.

Sign in to see which connections each card needs are ready.

You stay in charge

  • Configuration is code you own. Workspaces, channels, connections and policies are EYG files, never YAML. They are evaluated, so a mistake is an error before it is a surprise.
  • Every effect is gated. Agents, triggers, subagents and people in the shell all run through the same channel shells. Secrets are never shown to programs, network secrets are added on the way out.
  • Agents propose, people decide. Agents must choose to post, trigger patterns cannot act at all, and anything an agent sets up is visible in the shell and the admin page.
  • No hidden API. The admin page uses the same HTTP API you can call, which runs the same effects your agents can be allowed to use.
  • Run it yourself. One process, your files, your keys, any model provider.

Run your own

You need Gleam and Erlang/OTP, and a key for a model provider, the example uses Ollama Cloud.

git clone https://github.com/CrowdHailer/eyg-lang && cd eyg-lang/packages/cloud
echo -n "$OLLAMA_API_KEY" | gleam run -m cloud/secrets -- set ../../examples/cloud/workspace.eyg OLLAMA_API_KEY
(cd ../example_chat && PORT=8080 gleam run) &
CLOUD=../../examples/cloud/cloud.eyg gleam run

Then open http://localhost:8081 and sign in first. The example workspace explains every channel.

Signing in. The first person to sign in to a new cloud is its admin, with every effect. Everyone after picks one of the shells in cloud.eyg. This example signs people in by name only, put the cloud behind your own authentication before others can reach it.
